# 解析基准：第一轮结论

语料：`bench/corpus/` 下 14 篇中文社科论文（综治中心主题），144 页，223,671 字符。
工具：`bench/run.py`（PyMuPDF 1.28.2，`get_text("blocks")` + `find_tables()`）。

## 结构指标

| 指标 | 结果 |
|---|---|
| 含图片的论文 | 0 / 14 |
| 有扫描页的论文 | 0 / 14 |
| 含表格的论文 | 3 / 14（4x4 一张、7x3 一张、7x7 一张） |
| 平均字符/页 | 1,553 |
| 空白页 | 0 |

## 表格抽检

- 4x4（理论视角对比表）：**完全正确**。
- 7x3（治理单元矛盾分布表）：**完全正确**，含 6 个数据行。
- 7x7（诸暨市综治中心功能分区表）：结构基本正确，但**合并单元格（rowspan）只落在首行**，后续行首列为空，需要 fill-down 后处理。这是"20% 长尾"，不是引擎问题。

## 文本层真正的问题

表格和扫描不是瓶颈，**行级 block 的排序与段落重建**才是：

1. `get_text("blocks")` 常把同一行切成多个 block（按 x 边界），不能直接拼接。
2. 页眉/页脚会混进 block 序列，且不一定在首尾。
3. 同一 y 的多个 block 需要按 x 排序后合并；双栏页需要先分栏、栏内按 y 排、再拼栏。
4. 脚注有两种形态：页底小字号 + ①② 标记（可按 y 与字号分离），以及正文内联的 `［8］`（保留在正文）。
5. 段落合并需要依据行宽、缩进、标点，不能只按空行。

## 决定

**不做 `engines/` 抽象。** 依据：

- 0 扫描页、0 图片、表格 21%，单一 PyMuPDF 覆盖全部样本。
- 引入引擎注册表只会增加维护面，不解决当前失败模式。
- 失败模式在**后处理**，不在抽取引擎。

保留一个函数级接缝即可：

```python
def read_pages(path: Path, pages: str | None = None) -> list[PageDoc]: ...
```

未来真出现扫描件或复杂图表，再加 `read_pages_mineru()`，用同一个返回类型替换，不建框架。

## 下一轮验证（后处理完成后）

对 14 篇自动检查：

- 页眉/页脚残留率
- 行序倒置数（y 非单调、同 y 的 x 逆序）
- 段落数/平均段长（与人工抽检对照）
- 脚注块是否正确分离
- 表格单元格准确率（人工抽检 3 张）

## v0.2 实现结果（回归）

`bench/regress.py` 跑 14 篇 / 144 页：

| 指标 | 结果 |
|---|---|
| 总段数 | 942 |
| 短段（<10 字） | 42 |
| 超长段（>1200 字） | 2 |
| 行序倒置 | **0** |
| 页眉残留 | **0** |
| 总耗时 | 4.8 s（约 33 ms/页） |

- 表格 3/3 抽出；合并单元格只补首列，7x7 表的 rowspan 已正确继承。
- 图 4 个：图题 + 图内文字单列（数值/类别分开），不做图像理解。
- 脚注从页底第一个标记起整体切出，含续行；参考文献若用 〔n〕 也会被归入脚注。
- 双栏页按栏切分，栏内按 y 排序；通栏元素（标题、摘要、关键词）单独成带。

已知残留：

- 扫描件无 OCR，只标记。
- 跨页表、无框线表仍可能出错。
- 图内文字顺序不可靠，需回原 PDF 核对。
- 首字下沉、页眉中的栏目名偶尔会留下一个短标题。

结论：单一 PyMuPDF + 后处理足够覆盖当前语料，不引入 `engines/`。
